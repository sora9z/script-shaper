# 문서 포맷 분석: KT Studio Genie_미녀는 괴로워_영문대본.docx

- 경로: `data/대본샘플들/KT Studio Genie_미녀는 괴로워_영문대본.docx`
- python-docx 기준 총 paragraph 5099개, 비어있지 않은 paragraph 3920개, table 0개.
- 분석 방법: 전체 paragraph를 `p.text`로 추출(빈 줄 포함) 후 처음 120개/중간 60개(index 1930~1990 부근)/끝 30개를 repr로 샘플링, 정규식으로 전체 스캔(순번/타임코드/화자 대문자 라인/(V.O.)(O.S.)/음악표시/콜론/INT.·EXT./대시 라인 등).

## 0. 결론 먼저

이 파일은 **스크린플레이(대본)도, "화자명: 대사" 리스트도 아니다.** SRT 자막 파일을 그대로 .docx로 옮겨놓은 **원본 자막(subtitle) 덤프**다. 화자명이 단 한 줄도 없고, 씬 헤더(INT./EXT.)도 없고, 지문(액션 라인)도 없다. 대신 SRT 3줄 블록(순번 → 타임코드 → 자막 텍스트 1~3줄) + 빈 줄 구분자 구조가 1179개 반복된다. 기존 파이프라인은 이 구조를 전혀 모르기 때문에, "화자명: 대사" 콜론 정규식이 **타임코드 줄을 화자-대사 패턴으로 오인식**해서 대량으로 오염시키는 실제 버그가 확인됐다 (아래 6번 참고, 실측치 포함).

## 1. 문서 유형: 스크린플레이? 자막/대사 리스트? 번호 체계?

**SRT 자막 파일이 .docx로 변환된 것.** 표준 SubRip(.srt) 3-라인 블록 구조를 그대로 따른다:

```
<순번>
<시작타임코드> --> <종료타임코드>
<자막 텍스트 1~n줄>
<빈 줄>
```

- 순번(`seq`) 라인: `^\d+$` 형태의 독립 paragraph. 1~1179까지 **끊김 없이 연속**(`seqs == list(range(1, 1180))` 확인됨). 총 1179개.
- 타임코드 라인: `HH:MM:SS,mmm --> HH:MM:SS,mmm` 형태. 역시 1179개, seq와 1:1 대응.
- 빈(공백) paragraph: 정확히 1179개. 즉 **SRT 블록 사이 구분자로 정확히 1개씩** 존재 — python-docx로 읽을 때 `len(para.text.strip()) > 0` 필터를 안 거치면 이 구분이 살아있지만, 실제 파이프라인(`utils/file_reader_list.py`)은 빈 줄을 이미 걸러내고 읽는다.
- 블록당 텍스트 줄 수 분포: 1줄 799개, 2줄 377개, 3줄 3개(전부 오프닝 크레딧 구간). 즉 대부분 자막 한 줄짜리 짧은 대사.
- 씬 번호/장(chapter) 구분, 표(table) 등 스크린플레이적 구조는 전혀 없음(`d.tables` == 0).

## 2. 화자명 표기

**화자명이 문서에 전혀 없다.** ALL-CAPS 이름 라인 0건, 콜론(`:`) 기반 "이름: 대사" 패턴 0건(문서 내 콜론이 들어간 줄은 전부 타임코드), 이름 단독 줄 0건. `프로젝트가 가정하는 "화자명 유형1/2"(콜론 구분, 3칸+ 공백 구분) 둘 다 이 문서에는 대응하는 실제 화자명 인스턴스가 존재하지 않는다.

대신 아래처럼 **순번/타임코드/텍스트** 3종류만 반복된다(각 3~5개 예시, repr):

```
'1'
'00:00:57,189 --> 00:00:59,248'
'<i>Presented by KM Culture</i>'
'583'
'00:52:37,922 --> 00:52:39,388'
'Think about it, Dad.'
'1171'
'01:52:25,590 --> 01:52:28,320'
'Assholes like you'
"would say so."
"You're sleeping her,"
```

화자 구분이 필요한 경우(두 사람이 한 자막 큐를 나눠 쓰는 경우)는 이름 대신 **줄 앞 대시(`- `)** 로만 표시된다(자세한 예시는 4번 참고). 화자명 텍스트 자체는 어디에도 없다.

## 3. 대사 vs 지문 vs 씬헤더 형식 신호

- **씬헤더(INT./EXT.)**: 0건. `^\s*(INT|EXT)[\.\s]` 정규식 매칭 0.
- **지문(액션 라인)**: 스크린플레이 특유의 "카메라 지문/행동 묘사" 단락 자체가 없음 — 있는 건 오직 대사 텍스트뿐. (괄호 지문 `()[]{}` 도 거의 안 보임 — 아래 4번 (V.O.)/(O.S.) 항목 참고.)
- **대사**: 순번+타임코드 블록 뒤에 오는 자유 텍스트 1~3줄. 문장부호는 영어식(`.` `,` `?` `!` `"` `...`)이며 한국어 어미(다/요/네 등)는 당연히 전무.
- 유일한 "형식 신호"는 **`<i>...</i>` HTML 유사 태그**와 **`#` 접두사(노래 가사)** — 이게 사실상 이 문서에서 "지문/화면자막 vs 대사"를 구분하는 유일한 마커다(아래 4번 참고).

## 4. 영어 대본 특유의 관례 존재 여부

일반적인 미국식 스크린플레이 관례(이름 단독 줄 뒤 대사 블록, `(V.O.)`/`(O.S.)`/`(CONT'D)` 등)는 **전혀 나타나지 않는다** (`(V.O.)`/`(O.S.)`/`(CONT'D)` 정규식 매칭 0건). 이 파일은 스크린플레이가 아니라 SRT이기 때문.

대신 SRT/자막 특유의 관례 3가지가 나타난다:

1. **`<i>...</i>` 리터럴 태그** (137개 non-empty paragraph에 포함): 화면 밖 목소리(내레이션/전화 목소리/오프닝 크레딧 등)를 나타내는 SRT 표준 이탤릭 마크업이 **문자 그대로 텍스트에 남아있음**. 실제 docx run의 `italic` 속성은 전부 `None`이며 (`p.runs[0].italic == None` 확인), 서식이 아니라 **날텍스트로 박제된 HTML 태그**다. 오프닝 크레딧(`<i>Presented by KM Culture</i>` 등)과 전화 통화/회상 대사에 주로 쓰임. 여러 줄에 걸쳐 열고 닫히는 경우도 있음(예: `'<i>in association with'` 다음 줄 `'Showbox/Mediaplex, Inc</i>'`).
2. **`#` 접두 노래 가사** (58줄): `"# I'm a beautiful girl"` 처럼 SRT에서 노래를 표시하는 관례. 대부분 `<i>` 없이 단독으로도 등장.
3. **대시(`-`) 접두 2인 대사 한 큐 배치** (16개 블록, 23줄): 한 자막 큐(같은 타임코드) 안에 서로 다른 화자의 짧은 대사 두 줄을 `- 대사1` / `- 대사2` 형태로 나눠 넣는 표준 자막 관례. 예:
   ```
   ['50', '00:04:11,385 --> 00:04:12,749', '<i>- Honey.', '- Yes?</i>']
   ['345', '00:33:39,983 --> 00:33:41,610', '- Hi.', '- Hi.']
   ['426', '00:41:00,123 --> 00:41:01,886', '- You okay?', '- What?']
   ```
   이게 사실상 이 문서에서 "화자가 바뀜"을 나타내는 유일한 신호이지만, 화자 이름 자체는 알 수 없음(익명 turn-taking 표시일 뿐).

## 5. 화자줄/이름줄 판정 regex 후보 (`^` 앵커) + 예외

이 문서에는 판정할 "화자명 줄"이 존재하지 않으므로, 오히려 필요한 건 **SRT 구조 요소를 화자-대사 패턴으로 오인식하지 않도록 제외하는 regex**다.

```python
# SRT 순번 줄 (제외 대상)
SRT_SEQ_RE = r"^\d+$"

# SRT 타임코드 줄 (제외 대상) — 기존 "화자명: 대사" 콜론 regex(r"^[^:\n]+:\s*")가
# 이 패턴에도 매칭되어 버그를 일으킴 (6번 참고)
SRT_TIMECODE_RE = r"^\d{2}:\d{2}:\d{2},\d{3}\s*-->\s*\d{2}:\d{2}:\d{2},\d{3}\s*$"

# 리터럴 이탤릭 태그 (스트립 대상, 화자 판정과 무관하지만 텍스트 정제 필요)
HTML_ITALIC_TAG_RE = r"</?i>"

# 노래 가사 마커 (제외 또는 별도 태깅 대상)
LYRIC_MARKER_RE = r"^#\s?"

# 2인 자막 큐 접두 대시 (화자 전환 신호로 활용 가능, 이름은 없음)
DUAL_SPEAKER_DASH_RE = r"^-\s+"
```

예외/주의사항:
- `SRT_TIMECODE_RE`를 라인 시작(`^`)과 끝(`$`) 모두 앵커링해야 한다. 시작 앵커만 쓰면(현재 콜론 regex처럼) 오탐이 발생.
- `DUAL_SPEAKER_DASH_RE`는 일반 대사에서도 등장할 수 있는 문장부호(예: "I—well—", 인용부호 안의 리스트 등)와 겹칠 수 있어 단독으로는 위험. SRT 블록 내에서 "2줄이면서 둘 다 대시로 시작"이라는 **블록 단위 컨텍스트** 없이는 신뢰도가 낮음.
- 참고용(이 문서엔 해당 사례 없음, 표준 미국식 스크린플레이 대비): 진짜 화자 이름 단독 줄은 보통 `r"^[A-Z][A-Z0-9 .'-]{1,30}(\s*\((V\.O\.|O\.S\.|CONT'D)\))?\s*$"` 형태(전체 대문자, 중앙 정렬, 이름 뒤 괄호 태그)로 판정하지만, 이 파일에는 대응 인스턴스가 0건이라 검증 불가.

## 6. 한국어 전제 프롬프트/로직이 이 문서에서 실패하는 지점

실제 파이프라인 함수(`utils.file_reader_list.read_file` → `utils.extract_speaker_and_dialogue.extract_speaker_and_dialogue`)를 이 파일에 그대로 돌려서 실측했다:

- `read_file()` 결과: 3920줄 (모든 non-empty paragraph, 순번/타임코드 포함)
- `extract_speaker_and_dialogue()` 결과: **1685줄이 "대사"로 추출됨**
- 그 중 **1179줄(70%)이 타임코드 줄 그 자체**(`00:00:57,189 --> 00:00:59,248` 형태)였다 — **전체 타임코드 1179개 중 1179개, 즉 100% 누수**.
  - 원인: `constants.SPEAKER_DIALOGUE_REGEX_LIST`의 1번 패턴 `r"^[^:\n]+:\s*"`(콜론 앞 화자명 제거용)가 `re.match`로 프리픽스만 확인하고 **전체 매칭을 요구하지 않기 때문에**, `"00:00:57,189 --> 00:00:59,248"`도 `"00"` + `:` 프리픽스로 매칭되어 그대로(치환 없이 원문 그대로) 대사 리스트에 append된다. 화자명 콜론 regex는 애초에 앵커링이 느슨해서 타임코드/시계 표기가 섞인 어떤 문서에도 이 문제가 재발할 수 있음(한국어 대본이라도 타임코드가 있으면 동일하게 터짐).
- 반대로 **진짜 대사는 대량 누락**된다: 순번/타임코드를 제외한 실제 텍스트 줄은 3920 - 1179 - 1179 = 1562줄인데, 이 중 실제로 "대사"로 뽑힌 건 1685 - 1179 = 506줄(약 32%)뿐. 나머지 68%(약 1056줄)는 드롭됨.
  - 원인: 마침표(`.`)로만 끝나는 평서문(`"Forget about him."`, `"But it's not."` 등)은 `.rstrip('.')` 후 한국어 어미 체크(`다/라/네/...`, `요/죠/...`)를 통과할 수 없어 **탈락**. `?`/`!`/`,`/`;`/`"` 등 언어 중립적 문장부호로 끝나는 줄만 살아남는데, 이는 우연히 통과하는 것이지 설계된 동작이 아님.
- **`<i>`/`</i>` 리터럴 태그가 정제되지 않고 그대로 남는다.** `data_processing.py`는 `()[]{}` 괄호 지문만 제거하고 `<...>` 태그를 다루는 로직이 없다. 137개 paragraph에 있는 `<i>`/`</i>`가 그대로 최종 텍스트/AI 입력/Word 출력에 노출되며, AI 20자 줄바꿈 프롬프트에도 잡음으로 들어가 글자 수 계산과 어절 분리를 왜곡시킬 수 있다.
- **화자명 제거 로직(`SPEAKER_DIALOGUE_REGEX_LIST`)이 애초에 무의미**하다 — 이 문서엔 제거할 화자명이 없으므로 정상 동작하더라도 얻는 게 없고, 위에서 본 것처럼 콜론 regex가 부작용만 일으킨다.
- **AI 프롬프트("한국어 구어체 어미 기준 ≤20자 줄바꿈")가 이 문서엔 개념적으로 안 맞는다** — 영어는 음절/어절 기준이 다르고("20자" 기준 자체가 한글 전제), 프롬프트가 "원문 표현을 바꾸지 말 것"을 강조해도 애초에 한국어 어미 언급이 영어 문장엔 적용 불가능한 지시라 모델이 혼란스러워할 가능성이 큼(직접 실행 테스트는 범위 밖).
- 대시(`- `) 2인 대사 큐는 화자 전환 정보인데, 현재 파이프라인은 이를 인식할 방법이 전혀 없어 두 화자의 말이 화자 구분 없이 섞인 채로(혹은 마침표로 끝나는 쪽은 아예 드롭된 채로) 출력된다.
